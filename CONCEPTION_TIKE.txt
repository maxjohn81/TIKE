TIKE - DOCUMENT DE CONCEPTION
Version : 1.0 - Document de travail à valider
Projet : Conception et développement d’un système informatisé de gestion de billetterie et de contrôle d’accès aux événements

IMPORTANT POUR L’AGENT DE DÉVELOPPEMENT
- Lire ce document et TACHES_TIKE.txt avant de modifier le code.
- Ne pas tout développer en une seule fois. Suivre les tâches dans l’ordre et attendre la validation de l’utilisateur aux étapes indiquées.
- Si le projet Java existe déjà, inspecter d’abord son arborescence, son build (Maven/Gradle), les dépendances et le code existant. Ne pas écraser un projet existant sans confirmation.
- L’interface doit rester ULTRA SIMPLE : fond clair, violet comme couleur principale, peu de boutons, libellés explicites, tableaux lisibles, formulaires courts, marges régulières. Pas d’animations décoratives ni d’interface surchargée.
- Ne jamais enregistrer un mot de passe en clair. Utiliser un hash adapté.
- Ne jamais simuler un paiement réel ni prétendre qu’un paiement Mobile Money est intégré. Les paiements électroniques sont enregistrés comme mode de paiement, sauf intégration expressément décidée plus tard.
- Toute opération financière ou réservation/vente doit être cohérente en base de données et utiliser des transactions SQL lorsque plusieurs tables sont modifiées.

1. PRÉSENTATION
Nom de l’application : TIKE
Slogan proposé : « Un billet, un accès, une expérience. »
Type : application de bureau Java Swing.
Base de données : SQLite embarquée, fichier local par poste.
Accès aux données : JDBC.
Domaine : vente/réservation de billets et contrôle d’accès aux événements.
Langue de l’interface : français.
Devise initiale : Ariary (Ar).
Plateforme visée : Windows en priorité.

2. OBJECTIF GÉNÉRAL
Permettre à une organisation de créer et publier des événements, gérer les lieux et les capacités, vendre ou réserver des billets, suivre les paiements, générer et imprimer des billets identifiés par QR Code, vérifier les billets à l’entrée et consulter les statistiques d’activité.

3. UTILISATEURS ET AUTORISATIONS
3.1 Administrateur
- Accès aux modules autorisés de l’application.
- Créer, modifier et désactiver les comptes utilisateurs.
- Gérer les événements, lieux, salles, catégories et tarifs.
- Consulter ventes, paiements, remboursements, journaux et statistiques.
- Les données historiques ne doivent pas être supprimées en cascade par erreur.

3.2 Agent de billetterie
- Consulter les événements ouverts à la vente.
- Rechercher/enregistrer un client.
- Créer une réservation si activée.
- Vendre des billets et enregistrer le paiement.
- Imprimer ou réimprimer un billet selon les règles.
- Consulter ses ventes, sans administrer les utilisateurs.

3.3 Contrôleur d’accès
- Rechercher un billet par identifiant ou lire un QR Code si une caméra compatible est disponible.
- Vérifier l’événement, le paiement, le statut et la date.
- Valider l’entrée une seule fois.
- Consulter le résultat de validation, sans accès aux fonctions financières complètes.

4. PÉRIMÈTRE FONCTIONNEL
M01 - Authentification et autorisations
- Connexion/déconnexion.
- Mots de passe hashés.
- Rôles : ADMIN, AGENT, CONTROLEUR.
- Vérification des autorisations avant d’ouvrir une fonctionnalité.
- Messages d’erreur simples et sans exposer de données sensibles.

M02 - Tableau de bord
- Nombre d’événements à venir/en vente.
- Billets vendus.
- Revenus encaissés.
- Réservations en attente.
- Dernières opérations.
- Les valeurs viennent de requêtes SQL réelles, pas de nombres codés en dur.

M03 - Événements
- Créer, consulter, modifier et rechercher un événement.
- Champs : nom, description, type, date/heure de début, date/heure de fin facultative, lieu/salle, statut.
- Statuts proposés : BROUILLON, PROGRAMME, EN_VENTE, COMPLET, ANNULE, TERMINE.
- Empêcher la vente si l’événement est annulé, terminé ou hors période de vente.
- Empêcher la suppression d’un événement ayant des ventes/historiques ; préférer le statut ANNULE.

M04 - Lieux et salles
- CRUD des lieux et salles.
- Champs lieu : nom, adresse, ville, description facultative.
- Champs salle : nom, lieu, capacité.
- Une salle ne peut pas être utilisée simultanément pour deux événements qui se chevauchent, si les dates/heures se recouvrent.
- La capacité totale des places configurées ne doit pas dépasser la capacité déclarée.

M05 - Places et catégories
- Deux modes à supporter dans la conception : places numérotées ou places libres. Pour la première version, commencer par les places libres avec capacité par catégorie, sauf validation contraire.
- Catégories de billets : nom, prix de base, quantité disponible, description facultative.
- Exemples : VIP, STANDARD, ÉCONOMIQUE.
- Le stock disponible doit être calculé ou mis à jour de façon cohérente.
- Si des places numérotées sont retenues plus tard, une place ne peut être vendue/réservée qu’une fois pour un événement.

M06 - Clients
- Enregistrer, modifier, rechercher et consulter les clients.
- Champs : nom complet, téléphone, e-mail facultatif.
- Éviter les doublons manifestes, notamment par téléphone si renseigné.
- Historique des billets, réservations et paiements associés.

M07 - Vente de billets
- Sélectionner événement, catégorie, client, quantité.
- Calculer automatiquement le montant.
- Valider disponibilité avant vente.
- Générer un numéro de vente et un billet unique pour chaque entrée.
- Une vente confirmée et son paiement doivent être enregistrés dans une transaction SQL.
- Interdire de vendre plus de billets que la quantité restante.
- Ne pas permettre de vente pour un événement annulé/terminé.
- Prévoir l’option de remise seulement si validée ; par défaut, aucune remise.

M08 - Réservations
- Réserver une quantité de billets pour un client, avec une date d’expiration.
- Statuts : EN_ATTENTE, CONFIRMEE, EXPIREE, ANNULEE.
- Les billets réservés ne sont pas valables pour entrer tant que la vente/le paiement n’est pas confirmé selon la règle adoptée.
- À l’expiration, libérer le stock de manière sûre.
- Pour la première version, l’expiration peut être vérifiée à l’ouverture du module et avant toute nouvelle vente ; une tâche planifiée n’est pas obligatoire.
- Éviter de réserver plus de billets que le stock restant.

M09 - Paiements
- Enregistrer les paiements en espèces, Mobile Money, carte ou virement comme méthodes déclaratives.
- Champs : vente, montant, méthode, date, référence facultative, statut.
- Statuts : EN_ATTENTE, PAYE, ECHEC, REMBOURSE/PARTIELLEMENT_REMBOURSE si nécessaire.
- Le billet ne devient VALIDÉ POUR ENTRÉE que si la vente est payée.
- Vérifier que le montant payé correspond au montant dû avant de finaliser une vente complète.
- Utiliser une transaction SQL pour vente + paiement + billets + mise à jour du stock.

M10 - Billets et impression
- Identifiant de billet unique et non devinable de façon triviale.
- Données imprimées : nom de l’événement, date/heure, lieu, catégorie, client si disponible, prix, identifiant et QR Code.
- Générer un QR Code contenant uniquement un identifiant/jeton de billet, pas de mot de passe ni de données personnelles inutiles.
- Prévoir aperçu et impression, ou export PDF si la bibliothèque choisie le permet.
- La réimpression ne doit pas créer un nouveau billet ni invalider l’original.

M11 - Contrôle d’accès
- Rechercher le billet par identifiant et, si le matériel/la bibliothèque le permet, lire un QR Code par caméra.
- Résultats : VALIDE, DEJA_UTILISE, NON_TROUVE, NON_PAYE, ANNULE, MAUVAIS_EVENEMENT.
- Enregistrer date/heure et contrôleur pour chaque tentative pertinente.
- Validation atomique : deux contrôleurs ne doivent pas pouvoir valider simultanément le même billet deux fois.
- Un billet accepté passe à UTILISE et ne peut plus être accepté une seconde fois.

M12 - Annulation et remboursement
- Réservations non payées : annulation et libération du stock.
- Vente payée : annulation/remboursement uniquement selon une règle définie par l’administrateur.
- Enregistrer l’opération et son motif dans l’historique.
- Ne jamais effacer silencieusement une vente payée.
- Après remboursement intégral, billet non utilisable ; le stock est libéré seulement si la politique et l’état de l’événement le permettent.

M13 - Statistiques et rapports
- Ventes par événement et période.
- Revenus encaissés par jour/mois/événement.
- Billets vendus et restants.
- Taux de remplissage = billets vendus / capacité disponible * 100.
- Répartition par catégorie et méthode de paiement.
- Export CSV en priorité ; PDF en option.
- Exclure les paiements annulés/échoués des revenus encaissés.

M14 - Historique/audit
- Journaliser les opérations importantes : connexion si retenue, création/modification d’événement, vente, paiement, annulation, remboursement, contrôle de billet.
- Champs : utilisateur, action, type d’objet, identifiant d’objet, date/heure, détails résumés.
- Le journal ne doit pas contenir de mots de passe ni de données de paiement sensibles.

M15 - Paramètres
- Nom de l’organisation, devise, durée de réservation, règles de remboursement.
- Valeurs par défaut simples.
- Protéger les paramètres sensibles par le rôle ADMIN.

5. RÈGLES MÉTIER OBLIGATOIRES
RB01 : Un billet possède un identifiant unique.
RB02 : Le stock ne peut jamais devenir négatif.
RB03 : Une vente doit vérifier et réserver/décrémenter le stock atomiquement.
RB04 : Une vente ne peut être finalisée si le montant payé n’est pas conforme à la règle de paiement.
RB05 : Un billet non payé, annulé ou remboursé ne donne pas accès à l’événement.
RB06 : Un billet ne peut être utilisé qu’une fois.
RB07 : Le contrôleur doit être autorisé à accéder au module de contrôle, mais pas aux fonctions administratives.
RB08 : Un événement annulé ou terminé n’accepte plus de vente.
RB09 : Toute annulation/remboursement conserve un historique.
RB10 : Les statistiques sont calculées depuis la base de données.
RB11 : Les opérations multi-tables critiques utilisent une transaction JDBC (commit/rollback).
RB12 : Les requêtes SQL utilisent PreparedStatement, jamais de concaténation de valeurs utilisateur.
RB13 : Les dates/heures sont stockées avec un type adapté et affichées selon le format local.
RB14 : Les erreurs sont présentées avec des messages compréhensibles, et les détails techniques vont dans les logs.

6. CONCEPTION DE LA BASE DE DONNÉES (PROPOSITION À VALIDER)
Utiliser SQLite. Toutes les tables ont une clé primaire. Les relations doivent avoir des clés étrangères, contraintes CHECK/UNIQUE/NOT NULL appropriées et index sur les champs de recherche fréquents.

Le schéma effectivement utilisé et initialisé par l'application est `src/main/resources/schema-sqlite.sql`. Il définit les clés entières `INTEGER PRIMARY KEY AUTOINCREMENT`, les relations, les contraintes, les index et la vue de stock. Les identifiants de billets sont stockés comme UUID texte ; les dates/heures sont stockées sous forme ISO locale.

Les tables métier sont : utilisateurs, lieux, salles, evenements, categories_billets, clients, ventes, vente_lignes, paiements, remboursements, billets, reservations, reservation_lignes, controles_acces et journal_activites. Le schéma versionné fait autorité afin que cette description reste cohérente avec l'application.

IMPORTANT : générer une ligne billet par unité achetée, même si la vente a une quantité supérieure à 1.

NOTE STOCK : ne pas modifier manuellement une colonne « disponible » depuis plusieurs endroits sans stratégie cohérente. Le stock restant peut être calculé à partir de quantités totales moins billets actifs vendus et réservations actives non expirées. Si un compteur est stocké pour la performance, sa mise à jour doit être atomique et testée. La méthode retenue doit être documentée dans le schéma SQL.

NOTE VERSION INITIALE : ce modèle est une proposition riche. Avant de créer toutes les tables, valider le périmètre. Une version scolaire peut commencer avec utilisateurs, lieux, salles, événements, catégories_billets, clients, ventes, vente_lignes, paiements, billets, controles_acces, journal_activites. Ajouter réservations et remboursements dans une phase suivante si le délai est court.

7. CONCEPTION DES INTERFACES
Style général :

- Violet foncé : #4C28A8.
- Violet clair : #F1ECFF.
- Fond : #F8F7FC.
- Texte : #242033.
- Succès : vert discret #2EAD69.
- Erreur : rouge discret #D64545.
- Police sans-serif simple, par exemple Segoe UI.
- Boutons avec libellés clairs, champs alignés, tables sobres.
- Une barre latérale violette, logo TIKE, nom du module actif et bouton de déconnexion.
- Pas de dégradés lourds, pas de cartes excessives, pas de tableaux de bord surchargés.
- Taille de fenêtre recommandée 1280x800, redimensionnable, centrée au lancement.
- Respecter le contraste et permettre le clavier lorsque possible.

Écrans :
UI01 Connexion
- Logo TIKE, nom d’utilisateur, mot de passe, bouton « Se connecter », message d’erreur.
- Aucun lien d’inscription publique si les comptes sont créés par l’administrateur.

UI02 Tableau de bord
- Quelques indicateurs : événements en vente, billets vendus, revenus encaissés, réservations en attente.
- Tableau des ventes récentes.
- Graphique simple facultatif ; ne pas retarder les fonctions métier pour le graphique.

UI03 Événements
- Tableau : nom, date, salle, statut, actions.
- Recherche et filtre de statut.
- Bouton « Nouvel événement » et formulaire simple.

UI04 Lieux et salles
- Liste des lieux/salles et formulaires simples.
- Affichage de la capacité.

UI05 Catégories et tarifs
- Liste des catégories par événement, prix et quantité totale.
- Validation du prix et de la quantité.

UI06 Clients
- Tableau : nom, téléphone, email.
- Recherche, ajouter, modifier, historique.

UI07 Vente de billets
- Sélecteur d’événement, client, catégorie, quantité.
- Afficher stock disponible, prix unitaire et total calculé.
- Bouton « Confirmer la vente » avec confirmation avant enregistrement.
- Résultat clair en cas de stock insuffisant.

UI08 Réservations
- Liste des réservations, statut et date d’expiration.

UI09 Billet/Impression
- Aperçu compact du billet, QR Code, numéro, événement, date, catégorie et client.

UI12 Statistiques et rapports
- Filtre de période et d’événement.
- Ventes, revenus encaissés, billets restants, taux de remplissage.
- Export CSV ; PDF facultatif.

UI13 Utilisateurs
- Réservé à l’administrateur.

UI14 Historique
- Tableau date, utilisateur, action, objet et détail.

UI15 Paramètres
- Paramètres généraux et durée de réservation.

NAVIGATION PROPOSÉE
Barre latérale : Tableau de bord, Événements, Lieux & salles, Clients, Ventes, Réservations, Contrôle d’accès, Rapports, Utilisateurs (admin), Historique, Paramètres, Déconnexion.
Masquer ou désactiver les entrées interdites au rôle connecté.

8. ARCHITECTURE JAVA PROPOSÉE
Ne pas mélanger SQL, règles métier et composants Swing.
Packages suggérés (à adapter au projet existant) :
- app : démarrage, configuration et session courante
- config : configuration de base de données
- model : objets métier
- dao : requêtes SQL et accès aux données
- service : règles métier et transactions
- ui : fenêtres/panels Swing
- ui.components : composants réutilisables
- util : validation, formatage, génération de codes/QR
- resources : icônes et styles
- db : schema-sqlite.sql et données de démonstration
Architecture conseillée : UI -> Service -> DAO -> SQLite.
Utiliser try-with-resources pour Connection/PreparedStatement/ResultSet.
Gérer les exceptions avec messages utilisateur lisibles et logs techniques.
Ne pas exécuter de requêtes longues sur l’Event Dispatch Thread ; si nécessaire, utiliser SwingWorker.
Ne pas coder de chemin de base en dur ; utiliser le dossier local de l’utilisateur, avec `TIKE_DB_PATH` comme réglage facultatif.

9. TESTS ET ACCEPTATION
- Connexion valide/invalide.
- Permissions selon rôle.
- Création/modification d’événement et validations de dates.
- Stock insuffisant : vente refusée sans données partielles.
- Vente réussie : paiement et billets créés, stock cohérent.
- Erreur pendant vente : rollback complet.
- Billet impayé/annulé : entrée refusée.
- Premier contrôle : accepté et marqué utilisé.
- Deuxième contrôle du même billet : refusé.
- Réservation expirée : stock libéré une seule fois.
- Statistiques cohérentes avec les ventes réelles.
- Aucune requête SQL par concaténation de saisie utilisateur.
- Mots de passe non stockés en clair.
- Test sur une base de données vide avec script d’initialisation.

10. DÉCISIONS À VALIDER AVANT LE DÉVELOPPEMENT
- Le projet Java existe-t-il déjà et utilise-t-il Maven ou Gradle ?
- Version de Java disponible.
- Le fichier SQLite doit-il rester dans l'emplacement local par défaut ou être déplacé par `TIKE_DB_PATH` ?
- Types d’événements : tous types ou seulement concerts/conférences ?
- Places : places libres d’abord ou places numérotées ?
- Réservations : incluses dès la version 1 ou phase 2 ?
- Contrôle QR : saisie du code d’abord, caméra ensuite si possible ?
- Impression : impression Java, PDF, ou les deux ?
- Le paiement est-il seulement enregistré dans l’application, sans intégration réelle ?
- Délai et nombre de membres du groupe.
